# AGENTS.md

## Основной принцип

Работай аккуратно, сохраняй существующее поведение и выбирай простые решения.
Соблюдай SRP, DRY, KISS и YAGNI. Не меняй несвязанные файлы и не создавай лишние уровни абстракции.

Перед задачей прочитай:
1. `plan.md` — требования, архитектура, баланс и этапы.
2. `README.md` — фактический статус, актуальные команды и устройство проекта.
3. Относящиеся к задаче файлы и локальные инструкции.

При расхождении плана и кода сначала проверь фактическое поведение. Не объявляй запланированную функциональность реализованной.

## Контекст проекта

word_guess — некоммерческая русскоязычная игра по механике «5 букв», веб-сервис с установкой как PWA.

Ключевые ограничения:
- Четыре режима: 4 буквы, 5 букв, 6 букв, кампания.
- Шесть попыток в партии; существительные, обработка повторяющихся букв.
- Свободная игра без энергии, рекламы, платежей и обязательного ожидания.
- Регистрация без подтверждения.
- Зеленый акцент, светлая/темная темы, адаптивность и reduced motion.
- Единственная БД — SQLite в Windows и Docker. Другую БД без указания пользователя не вводить.
- В словаре минимум по 1000 разных существительных каждой длины; количество подтверждать отчетом.
- Победы приносят очки и монеты, каждые десять уровней кампании — сундук.
- Не копировать брендинг Т-Банка; ref1.jpg и ref2.jpg служат референсами механики.

Подробные правила, цены, вероятности и ограничения находятся в plan.md.
Изменения требований пользователя имеют приоритет над планом.

## Среда и запуск

Основная среда: Windows, PowerShell, Python .venv и Node.js.
Локальные команды пиши для PowerShell; npm в сценариях Windows вызывай через npm.cmd, если это требуется средой.
Linux-команды допустимы внутри Dockerfile/контейнеров.

Поддерживай оба способа запуска: `docker compose up --build` и `run.bat` без Docker.
Не устанавливай глобальное ПО, не удаляй БД и не сбрасывай пользовательский прогресс ради запуска.
Учитывай пути с пробелами. Секреты, .venv, node_modules и runtime-БД не коммить.

## Архитектура и целостность данных

Frontend: React + TypeScript + Vite. Backend: FastAPI. Хранение: SQLite + SQLAlchemy + Alembic.
Конкретные версии и команды фиксируются при реализации в lock-файлах и README.

- Игровой ответ, проверка попыток, награды, баланс и розыгрыш — ответственность сервера.
- Не передавай скрытые ответы/словари ответов клиенту до завершения партии.
- Покупки, расход предметов, победы и сундуки проводи атомарно и идемпотентно.
- Повторы запросов, две вкладки и потеря ответа не должны дублировать операции.
- Проверяй принадлежность объектов пользователю; не доверяй присланным клиентом очкам и ценам.
- Включай SQLite foreign_keys, WAL и busy_timeout; используй короткие транзакции.
- Не рассчитывай на SELECT FOR UPDATE для блокировки строк SQLite.
- Изменяй схему через миграции. Seed должен быть повторяемым без дублей.
- Одна активная партия на пользователя и режим; прогресс восстанавливается после перезагрузки.
- После проигрыша кампании следующая попытка получает другое слово по правилам plan.md.
- Пароли хешируй Argon2id, сессии храни через HttpOnly cookie; не помещай токены в localStorage.
- Баланс и игровые правила держи в одном серверном источнике, не дублируй формулы в UI.

## Контент и интерфейс

Не генерируй выдуманные слова для выполнения количественного требования.
Проверяй часть речи, форму, длину и дубли после нормализации «ё/е».
Сохраняй происхождение словарных данных и лицензии обработанных наборов.

Музыку и внешние материалы используй только с проверенной лицензией.
Храни нужные файлы локально и добавляй атрибуцию в THIRD_PARTY_NOTICES.md.
Не начинай загрузку музыки с автозапуском в обход правил браузера.

Поддерживай обе темы, экранную и физическую клавиатуру, видимый фокус и доступные подписи.
Не обозначай статус буквы только цветом. Уважай prefers-reduced-motion.
Анимация сундука показывает уже определенный сервером приз; ее пропуск не меняет награду.

## Размер и организация файлов

Цель для исходного кода — 150–250 строк; при приближении к 300 подумай о разделении.
Новые вручную написанные исходные файлы не должны превышать 400 строк.
Не обходи ограничение минификацией, длинными строками или огромными компонентами.

Ограничение не распространяется на документацию, словари, lock-файлы, миграции автогенерации и другие машинные данные.
Не дроби словарь на искусственные части только ради лимита строк.

## Проверки

Выбирай проверки по затронутому поведению:
- Игровое ядро: pytest для повторов букв, валидации, подсказок и подсчета наград.
- SQLite/экономика: API и конкурентные запросы, повторные операции, откат транзакций.
- Интерфейс: TypeScript/build, значимые проверки Vitest, нужные сценарии Playwright.
- Контент: отчет количества/уникальности/длины и проверка включения лицензий.
- Инфраструктура: чистый и повторный запуск Docker/Windows, сохранность БД.

Запускай только реально существующие команды; актуальные команды документируй в README.
Полный прогон нужен для общей инфраструктуры, итоговой приемки или прямого запроса.
Не повторяй прошедшие проверки без новых изменений или конкретного риска.
Изменение одной документации не требует запуска тестов приложения.

## Документация и версии

Держи документацию минимальной:
- plan.md — требования, решения, этапы и проверенный статус.
- README.md — фактический запуск, конфигурация и обслуживание.
- CHANGELOG.md — реализованные изменения версий.
- THIRD_PARTY_NOTICES.md — внешние материалы и лицензии.

README.md — обязательный поддерживаемый документ проекта. Обновляй его в той же задаче, если меняются:
- фактический статус и доступные возможности;
- требования к окружению, зависимости и команды запуска/остановки;
- переменные окружения, конфигурация и структура каталогов;
- расположение SQLite, миграции, импорт слов, backup/restore;
- установка PWA, ограничения подключения и команды проверок.

Публикуй в README только проверенные инструкции; будущие возможности и команды явно помечай как планируемые.
При изменении пользовательского поведения проверь актуальность README, даже если подробные правила остаются в плане.
Перед завершением задачи отдельно проверь, нужно ли обновить README, и обнови его при необходимости.

Не создавай дублирующие документы без необходимости.
Используй версию Major.Minor.Build: major — несовместимые изменения, minor — функциональность, build — исправления.
Версия хранится в одном месте в коде и отображается в интерфейсе.
Правки только планов и документации не требуют выпуска новой версии приложения.
